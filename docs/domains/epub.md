# EPUB domain

## Overview

`src/formats/epub` decodes EPUB 2 and EPUB 3 files into the core `Book` model. It consumes the zip reader (`src/zip`) for container access and registers through the public format seam as `epub: BookFormat` (re-exported from `src/formats/index.ts`), so `open(bytes, { formats: [epub] })` is the whole integration. Modules: `index.ts` (sniffer, decoder, zip→core error bridge, `Book` assembly, fallback-chain resolution), `opf.ts` (container document + OPF package parsing into plain data), `toc.ts` (nav-document and NCX TOC extraction), `href.ts` (href → zip-entry-name resolution), `xml.ts` (the internal XML parser and element helpers). Format knowledge comes from the W3C EPUB 3 / OCF / OPF specifications only.

## Key decisions

- **XML is parsed by a minimal internal parser, not `DOMParser`** (2026-08-24). Node has no `DOMParser`, decoder tests must run headless under `node:test`, and zero runtime dependencies forbids an XML library; running decoder correctness under Playwright would make a browser a test gate, which the tooling stance rejects. So `xml.ts` implements a small well-formed-XML walk sufficient for the four spec-defined structural documents the decoder reads: container.xml, the OPF, the NCX, and the EPUB 3 nav document. It lives entirely inside `src/formats/epub` — no XML surface or environment shim leaks into `src/core`. Its limits are deliberate (see Gotchas); chapter content is never parsed by it.
- **All hrefs resolve relative to the document that carries them.** Manifest/spine/guide/cover hrefs resolve against the OPF's directory; nav-document and NCX targets resolve against *their own* document's directory (the two differ whenever the TOC document does not sit next to the OPF). `href.ts` normalizes `.`/`..` segments, percent-decodes per segment (malformed percent-escapes stay literal rather than throwing), splits off the fragment, and treats scheme-carrying references (`http:`, `mailto:`) as unresolvable. An unresolvable manifest href falls back to the verbatim string, so the failure surfaces lazily as a typed missing-entry error on `load()`, never as a decode crash.
- **`Section.resolve()` is manifest-keyed, section-relative, and refuses anything it cannot actually serve** (2026-08-24). The decoder builds one path → `Resource` map over the **whole** manifest — spine items included — and each section closes over its *own content directory* (`directoryOf` of the path `load()` reads, which is the fallback target's path when a fallback supplied the content), never the OPF's. A chapter at `OEBPS/text/ch1.xhtml` therefore reaches `../images/x.png` at `OEBPS/images/x.png`; resolving against the OPF's `OEBPS/` would climb one level too far. Three consequences, each deliberate:
  - **Spine items resolve.** `Book.resources` excludes spine items, so a link to another chapter or a spine-listed SVG would otherwise dead-end; keying the resolver by path instead of by manifest id makes them fall through naturally, and a reference gets the media type the manifest declares for *that file* regardless of any fallback chain built on it.
  - **The manifest is the only source of a media type**, so a file present in the zip but undeclared in the manifest does not resolve — a spec violation the resolver reports as unresolvable rather than guessing a type from a file extension.
  - **A declared item whose zip entry is absent does not resolve either.** This is the one place the decoder does *not* defer a missing entry to a lazy `load()` failure: a consumer builds a URL from the result, and it must learn the reference is dead before it does.
- **`Section.resolveHref()` reuses the TOC's path → section-id table** (2026-08-26). The navigation twin of `resolve` (see [`docs/domains/core.md`](core.md)): it resolves a section-relative href with the same `href.ts` `resolveHref(contentDir, ref)` used everywhere else, then looks the resulting entry name up in `sectionByPath` — the very map the TOC is built from, which keys **both** the spine item's own href and its fallback target's path to the section id. So a "next chapter" link, or a link inside a rendered in-content nav, lands on the right section by the same authority a TOC entry does, and a fragment on the href rides through untouched. It returns `undefined` for anything `sectionByPath` does not name (a resource, an absolute/scheme href, a missing target), i.e. the reader soft-misses rather than throwing. The closure reads `sectionByPath` live — it is fully populated by the time any click fires — so no ordering dance is needed even though the map finishes filling after the section objects are pushed.
- **TOC precedence: the EPUB 3 nav document wins; the NCX is the fallback; a broken TOC never fails the book.** The nav document is discovered via `properties="nav"`, the NCX via the spine's `toc` attribute and then by `application/x-dtbncx+xml` media type. A nav document that is missing, malformed, or yields zero entries falls through to the NCX; if that fails too, `toc` is `[]` — TOC damage degrades, the book still opens. TOC entries whose target cannot be mapped to a spine section borrow their first child's section (heading-only `<li><span>` groups, navPoints pointing outside the spine); entries with no resolvable target anywhere are dropped.
- **Manifest fallback chains resolve at decode time, with cycle detection.** A spine item whose media type is not renderable (`application/xhtml+xml`, `image/svg+xml`, `text/html`) follows its `fallback` attribute until a renderable item is found; the section keeps the *spine item's* id but takes the fallback target's media type and bytes. A chain that revisits an id raises `CorruptContainerError`; a chain that dead-ends leaves the original item in place (the consumer sees the foreign media type and decides).
- **RTL and fixed-layout are flags on the model, nothing more.** The spine's `page-progression-direction` becomes `Book.direction` (`'ltr' | 'rtl'`, omitted for `default`/absent); a package-level `<meta property="rendition:layout">pre-paginated</meta>` becomes `Book.fixedLayout: true` (`reflowable` → `false`, absent → omitted). Fixed-layout *rendering* is permanently out of scope — the flag exists so hosts can refuse or warn, never so a layout path can branch on it.
- **The decoder is the zip→core error bridge.** `src/zip` throws zip-local errors and knows nothing about core; every zip call in the decoder goes through a bridge that rethrows `ZipEncryptedEntryError` as `EncryptedContentError` and any other `ZipError` (malformed structures, missing entries, truncation) as `CorruptContainerError`, always with the zip error as `cause`. A raw `ZipError` never escapes `open()`.
- **Sniffing opens the archive rather than trusting byte offsets.** After a cheap `PK\x03\x04` check, the sniffer reads the `mimetype` entry through the zip reader and compares against `application/epub+zip`. This tolerates real-world archives where `mimetype` is not the first entry or is compressed (both OCF violations); any sniff-time failure returns `false`, never throws. Trailing whitespace after the media type (commonly a newline) is tolerated via `trimEnd()`; leading garbage is not.
- **Namespace handling is by local name, not URI resolution.** Elements and attributes match on the name after the prefix (`dc:title` → `title`, `opf:role` → `role`); `xmlns` declarations are ignored. The two package documents use small, distinctive vocabularies where local names do not collide, and this also absorbs publishers who use nonstandard prefixes or a default namespace.
- **Cover detection prefers EPUB 3, falls back to EPUB 2.** A manifest item with `properties` containing `cover-image` wins; otherwise `<meta name="cover" content="...">` in the metadata resolves by manifest id, then by href (some publishers put the image href in `content` instead of the item id). No cover means `metadata.cover` is omitted — never an error.

## Implementation notes

- Decode flow: open zip → read `META-INF/container.xml` → first `<rootfile>` with `media-type="application/oebps-package+xml"` (or the first rootfile at all) gives the OPF path → parse the OPF into an `OpfPackage` → assemble the `Book`. Malformed container or OPF XML is caught and wrapped in `CorruptContainerError` with the parse error as `cause`.
- `OpfPackage` (`opf.ts`) keeps everything later work needs: the OPF path (hrefs resolve relative to its directory), the full manifest (`id`/`href`/`media-type`/`properties`), spine idrefs in order, and `<guide>` references. The `Book` uses a subset; TOC and resource-resolution work read the rest without re-parsing.
- Sections are the spine itemrefs resolved through the manifest, in spine order, with the manifest item id as section id; `linear="no"` itemrefs are included. Idrefs that resolve to no manifest item, and duplicate idrefs, are skipped rather than fatal. Non-spine manifest items become the `resources` map, keyed by manifest id (the nav document and NCX stay available there).
- Section/resource `load()` is lazy through the zip reader, keyed by the resolved entry name computed once at decode time. Sections carry `scripted: true` when either the spine item or its fallback target declares `properties="scripted"`; the flag is omitted otherwise.
- TOC targets map to sections through a resolved-entry-name → section-id table built while assembling the spine; both the spine item's own path and its fallback target's path map to the section, so a nav that points at the original href still lands when a fallback supplies the bytes. Pure-fragment targets (`#anchor`) resolve against the TOC document itself. Labels are deep document-order text (inline markup contributes, `&nbsp;` decodes) with whitespace collapsed.
- Package documents decode as UTF-8, or UTF-16 when a BOM says so — the encodings the EPUB spec allows.
- Fixtures in `test/fixtures/epub/` are generated by `make-epub-fixtures.mjs` in that same directory (invented text, byte-level zip writer that keeps `mimetype` first and stored, real 1×1 PNGs for covers). Corrupt-container and non-EPUB fixtures cover each failure mode; dedicated fixtures cover nav-only/NCX-only/both TOCs, an `OEBPS/`-style subdirectory OPF with `../` and percent-encoded hrefs whose chapter markup carries the section-relative references (plus one manifest item deliberately missing from the archive) that `Section.resolve()` is tested against, fallback chains (including a circular one), the `nav`/`cover-image`/`scripted` properties, an RTL spine, and pre-paginated metadata.
- `test/corpus/` (gitignored, `npm run fetch-corpus`) holds Gutenberg/Standard Ebooks titles plus a hostile subset of the W3C EPUB 3.3 test suite under `epub-testsuite/` (built books served from `w3c.github.io/epub-tests/tests/<id>.epub`). Corpus tests skip when the directory is absent; the real books additionally verify `load()` returns markup bytes and every TOC entry targets a real section — structure-only assertions once let a resolution bug survive because nothing ever loaded a section.

## Gotchas

- **The internal XML parser is not a conforming XML processor.** It handles elements, attributes (quoted only), text, CDATA, comments, processing instructions, and skips DOCTYPE declarations (including internal subsets) without reading them. It does **not** support: DTD-defined entities (only the five predefined ones plus `&nbsp;` and numeric character references decode; unknown entities stay literal), namespace URI resolution, attribute-value normalization beyond entity decoding, or well-formedness checks it doesn't need (it does reject mismatched/unclosed tags, a missing root, and a second root element). Its reach ends at the structural documents (container, OPF, NCX, nav document) — never chapter content. A nav document is XHTML, so an HTML named entity beyond `nbsp` shows up literally in a label (`&mdash;` stays `&mdash;`), and a nav that is not well-formed XML falls through to the NCX rather than failing the book.
- The spec says `mimetype` must be first and stored; sniffing deliberately does not verify placement or method, only content. Do not "fix" the sniffer to enforce the spec — real books violate it.
- `<meta name="cover">` vs EPUB 3 `<meta property="...">` share a local name; they are distinguished by attributes, not element name. The EPUB 2 cover meta is matched only when `name="cover"` is present.
- Gutenberg EPUB3 builds and Standard Ebooks declare the cover **both** ways (`properties="cover-image"` on the item *and* an EPUB 2 `<meta name="cover">`), so the corpus never reaches the EPUB 2 fallback — only the committed EPUB 2 fixture proves that path. Standard Ebooks' `<meta name="cover" content="cover.jpg">` uses an item id that looks like a filename; resolution is by id first for exactly this reason.
- Gutenberg EPUB3 builds ship far more TOC entries than spine sections (Moby Dick: 146 entries into 12 sections) — many nav anchors share one section and differ only by fragment. Never assume TOC entries and sections correspond one-to-one.
- **`resolve()` returning `undefined` is not always a broken book.** Absolute URLs, `data:` URIs, `mailto:`-style scheme-carrying links and fragment-only references (`#anchor`, which targets the section itself) all return `undefined` by design; only a caller that treats every `undefined` as damage will be surprised. `resolve()` discards any fragment on the reference — `chapter-2.xhtml#part` resolves to the document, and the fragment is the caller's to keep.
- **Font obfuscation is not implemented, and it is decoder work when it is.** The corpus carries `ocf-font_obfuscation.epub`; its fonts decode to garbage and simply fail to load, so text falls back to the next family in the stack rather than breaking. De-obfuscation (the IDPF/Adobe algorithms, keyed off the package identifier) belongs here rather than in the view, which has no business knowing a resource was scrambled. Worth a task only when a real book makes it visible.
- The W3C test suite's `pub-foreign_bad-fallback` names a fallback id that resolves nowhere renderable; the dead-end rule (keep the original foreign item) is what lets it decode instead of erroring.
- `exactOptionalPropertyTypes`: `BookMetadata`, `OpfPackage`, `TocItem`, and `Section` optional fields are built with conditional spreads — never assign `undefined`.

## Patterns

- **Every real-world divergence becomes a minimal committed fixture with a test before the workaround lands.** The fiddly parts (TOC shape, href resolution, fallbacks) are exactly where publisher files diverge from spec; a corpus book that exposes a bug is reduced to an invented, license-clean fixture in `make-epub-fixtures.mjs` so the regression outlives corpus availability. This is an ongoing practice, not a one-off.
