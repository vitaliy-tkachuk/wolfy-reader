# Tooling domain

## Overview

The repo skeleton and dev tooling: `package.json`, `tsconfig.json`, npm scripts, the corpus download script (`scripts/fetch-corpus.mjs`), the demo dev server (`scripts/serve-demo.mjs`), the headless-core purity check (`scripts/check-core-purity.mjs`), `.gitignore` rules, and the source directory layout (`src/core`, `src/zip`, `src/formats`, `src/layout`, `src/view`, `test/`, `demo/`). There is deliberately no bundler, CI, lint tooling, or publishing config — that apparatus belongs to the release milestone, not to day-one development.

## Key decisions

- **Three devDependencies: `typescript` (7.x native compiler), `@types/node`, and `playwright`.** All latest stable. Nothing is ever added at runtime — `dependencies` stays `{}` permanently, so the zero-runtime-dependencies claim is untouched. Playwright is the recorded browser-test stack and earns its place because layout questions (fragmentation, containment, re-layout cost) cannot be answered headlessly; see [`layout.md`](layout.md).
- **Browser tests launch full Chromium (`channel: 'chromium'`), not Playwright's default headless shell.** The shell is a stripped build with a different compositor path — the wrong thing to measure CSS multi-column layout, `content-visibility`, and paint timing on.
- **`module`/`moduleResolution: nodenext`** rather than `bundler`: there is no bundler by design, and `nodenext` keeps `tsc` output (once emit starts) directly loadable by both Node and browsers.
- **Relative imports carry `.ts` extensions, rewritten to `.js` on emit** (`allowImportingTsExtensions` + `rewriteRelativeImportExtensions`). This is what lets a `.ts` test import `../src/zip/index.ts` and run under Node's type stripping with no build step. A `.js`-extension import would resolve at build time but break every headless test run, because type stripping does not map `.js` back to `.ts`.
- **`noEmit: true`** — `tsc` is a typechecker only at this stage; no build output exists, so `dist/` stays empty and gitignored until packaging work begins.
- **Tests via bare `node:test`**, written in TypeScript and invoked with a glob (`node --test "test/**/*.test.ts"`). Node runs them directly via type stripping — no transpile step, no test framework. A directory argument (`node --test test/`) fails on Windows — Node tries to resolve it as a module — so the glob form is the portable one.
- **The browser tier is `node:test` too, driving Playwright from the outside.** Suites live in `test/browser/*.browser.mjs` and run under `npm run test:browser`; the `.browser.mjs` suffix keeps them out of the default `test/**/*.test.ts` glob, so `npm test` stays headless and fast. Using `node:test` rather than a second runner means one reporter, one assertion library, and `describe`/`test` semantics that already match the rest of the suite. A missing Playwright install skips the whole file with a message instead of failing, the way the corpus tests skip a missing download.
- **The browser suites drive a page, and read the sandboxed frame through Playwright rather than through the page.** The host page provably cannot see into an opaque-origin frame — that is the thing under test — so assertions about the rendered document evaluate in the frame directly (`page.mainFrame().childFrames()`), which CDP reaches regardless of origin. A test that reached the frame's DOM from the host page would be proving the isolation had failed.
- **The demo runs over `http://localhost`, never `file://`.** Browsers block ES module loading (and most useful APIs) on `file://` pages, and the project's browser tooling refuses `file://` URLs, so the demo needs a real origin. `npm run demo` starts a zero-dependency server built on Node built-ins — no `serve`, no `vite`, in keeping with the no-new-devDependencies rule.
- **The demo server exposes exactly two mounts by default: `demo/` at `/` and `src/` at `/src/`.** `/` maps to `demo/index.html`, and `/src/...` serves the library modules the demo imports. Nothing else in the repo is reachable over HTTP.
- **Mounts are a parameter, and the default set is the only one `npm run demo` ever uses.** `scripts/serve-demo.mjs` exports `startServer({ mounts, port })` so the browser test harness can add its own (`test/browser/`, `test/fixtures/epub/`, `test/corpus/`) and take an ephemeral port with `port: 0`. The alternative — a second server — would duplicate the type-stripping logic, which is the non-trivial part. The widening is opt-in and lives in the test harness; the deliberately narrow default is unchanged.
- **The server strips TypeScript types on the way out, so the browser runs `src/` directly.** Browsers cannot execute type annotations; each `.ts` response is passed through `stripTypeScriptTypes` from `node:module` with `mode: 'strip'`, which blanks type syntax in place and preserves line/column numbers, so browser stack traces point at the real source. Stripped output keeps its relative `./x.ts` specifiers; the browser requests those and each is stripped in turn, so the whole import graph works transitively. No bundler, no build step, no dependency — `node:module` is a built-in.
- **Corpus is downloaded, never committed.** `test/corpus/` is gitignored; only small license-clean fixtures live in `test/fixtures/` (committed).
- **`npm run check:core` guards the headless core, and it is enforced from before there is anything to guard.** Nothing reachable from `src/core/index.ts` may import `src/layout` or `src/view`. The cost is not only bundle weight: view modules touch `document`/`window`, so without a guaranteed-headless entry a Node consumer importing `.` risks a **throw on import**. The guard is cheap while `src/view` is still a placeholder and expensive once view imports have accumulated silently, so it ships as a standalone npm script rather than waiting for CI. CI (`PLAN.md` MR-2) **adopts** this script; it does not author it.
- **The check is a static source walk, not a parse and not a build.** `scripts/check-core-purity.mjs` uses Node built-ins only (`node:fs/promises`, `node:path`, `node:url`), matching the shape of the other `scripts/`. It walks the real import graph from `src/core/index.ts` — resolving `.ts`-extension specifiers against each importer's directory and memoizing — so it needs neither a compile step nor a bundle. A parser would be a new dependency and `tsc`'s API would be a build step, both disproportionate to a graph a few dozen files wide with a uniform import style.
- **`import type` fails the check like a value import.** `verbatimModuleSyntax` erases it at runtime, so it costs nothing in bundle terms, but it is still a design-boundary violation and permitting it invites a later value import to slip in behind one.
- **The constraint is one-directional.** `src/view` importing `src/core` is correct and passes; only the core → {layout, view} direction fails.
- **Failures report the whole chain, not the offending file.** `src/core/index.ts -> src/core/book.ts -> src/layout/index.ts` says which edge to cut; a bare filename does not. All violations are reported in one run rather than only the first.

## Implementation notes

- npm scripts: `npm test` (node:test glob run over `test/**/*.test.ts`), `npm run test:browser` (node:test over `test/browser/*.browser.mjs`, driving Playwright), `npm run typecheck` (`tsc --noEmit`), `npm run check:core` (`node scripts/check-core-purity.mjs`), `npm run fetch-corpus` (`node scripts/fetch-corpus.mjs`), `npm run demo` (`node scripts/serve-demo.mjs`), `npm run bench` (`node bench/run.mjs`, the pagination benchmark).
- `scripts/check-core-purity.mjs` scans each file for `import`/`export … from`, side-effect `import '…'`, and literal dynamic `import('…')`, after blanking comments so a commented-out import is never walked. It catches `export … from` re-exports deliberately: `src/core/index.ts` is almost entirely re-exports, so an import-only scan would walk one module and pass vacuously. A clean run prints the module count for exactly that reason — a count of 1 or 2 means the walker stopped at the barrel. Resolution tries the specifier as written, then `+ .ts`, then `/index.ts`. A specifier resolving outside `src/` is a leaf; a bare specifier is a hard failure with its own message, since `dependencies` stays `{}` permanently.
- `scripts/make-bench-fixture.mjs` generates the benchmark fixtures into gitignored `bench/fixtures/`: a 500KB+ synthetic single section assembled from real corpus prose via a seeded PRNG (byte-identical across runs — no `Math.random()`), and the largest real corpus section extracted through the public API. Both are sanitized body fragments with no scripts, styles, or external references. It skips with exit 0 when `test/corpus/` is absent.
- A plain `.mjs` script can `import { open } from '../src/core/index.ts'` directly under Node's type stripping — no `stripTypeScriptTypes` call needed, unlike the demo server, which needs it because it ships source *to a browser*. A dynamic `import()` of a Windows absolute path does need `pathToFileURL`; a static relative import sidesteps it.
- `scripts/serve-demo.mjs` uses only Node built-ins (`node:http`, `node:fs/promises`, `node:module`, `node:path`, `node:url`). It listens on port 8080 by default, walks up to the next free port if 8080 is busy (failing with a clear message if none of 8080–8089 is free), and prints the URL. It serves `.ts` files as `text/javascript` with types stripped so browsers accept and run them as modules, resolves each request against its mount (`demo/` or `src/`) and 404s any path that escapes it, and answers missing files with a plain 404 that leaks no filesystem paths. A `.ts` file that fails to strip answers 500 with the message, so a syntax error surfaces in the network panel instead of as a silent module failure.
- `tsconfig.json` includes `src/` and `test/`, so tests are typechecked alongside the source they exercise. Each `src/` subdirectory holds a placeholder `index.ts` containing `export {}` — real modules replace them as milestones land.
- `scripts/fetch-corpus.mjs` uses only Node built-ins (`fetch`, `node:fs/promises`, `node:path`, `node:url`). It downloads Gutenberg titles as EPUB+TXT *pairs* (same title in both formats feeds differential decoder testing) plus a Standard Ebooks EPUB, is idempotent (skips files already present), and exits non-zero if any download fails.
- `demo/index.html` is one self-contained, framework-free file that exercises the library through the public API only (`open` from `/src/core/index.ts`, `epub` from `/src/formats/index.ts`, `ContentHost` from `/src/view/index.ts`). Pick a file and it shows what the decoder produced: metadata plus section count, the cover rendered from the cover `Resource` bytes via a `blob:` URL (revoked on replacement — the demo page has its own origin, so blob URLs work here where they cannot inside the content frame), badges for `direction` and `fixedLayout`, the nested clickable TOC, and the reading order. Clicking an entry renders that section as live markup in the sandboxed host, with a panel listing what the sanitizer removed or unwrapped, which references were served or refused, and any CSP violation the frame reported — the observable proof that the security layers ran. Renders are chained on a promise because the host refuses a superseded render. Typed decode errors display by class name (`UnrecognizedFormatError`, `CorruptContainerError`, `EncryptedContentError`).
- `test/browser/harness.html` is the browser tier's page: it opens books through the public API, drives a `ContentHost`, collects violations and frame messages, and counts `URL.createObjectURL` calls so a test can assert the host mints none. It also exposes two deliberate attacks on the protocol — a well-formed message posted by the top window, and a sibling frame reaching `parent.frames[0]` — so both source checks are exercised from the outside.

## Gotchas

- `stripTypeScriptTypes` emits an `ExperimentalWarning` on first use. The server replaces the default `warning` listener with one that drops exactly that warning and prints everything else — do not suppress warnings process-wide (`--no-warnings` would hide real ones).
- The demo server deliberately does not serve the repo root. Any browser tab can issue requests to localhost, so a root mount would put `.git/` (whose config can carry remote URLs with embedded credentials), the multi-megabyte downloaded corpus, and gitignored local scratch on the wire. Only `demo/` and `src/` are exposed by `npm run demo`; the test harness passes wider mounts explicitly and binds an ephemeral port for the life of one test run.
- A browser test that leaves an extra iframe in the harness page breaks any later test that identifies the content frame positionally — Playwright's `childFrames()` order is attach order, not document order. The protocol spoof test removes its sibling frame again, and `contentFrame()` asserts there is exactly one child frame rather than trusting an index.

- `tsc --noEmit` errors with "no inputs were found" if `src/` holds only `.gitkeep` files — the placeholder `export {}` modules are what keep the typecheck green, so don't replace them with bare `.gitkeep`s.
- Node's type stripping resolves import specifiers literally. An internal `import './dep.js'` throws at test time even though it typechecks — always write `./dep.ts`.
- The purity check's source scan assumes the repo's uniform import style: declarations start a line and every specifier is a string literal. A dynamic `import()` with a computed specifier cannot be followed — the script warns on stderr rather than failing, so an unfollowable edge is visible instead of silently trusted. If `src/` ever adopts computed specifiers or a non-literal re-export indirection, the scan needs to grow, not the boundary.
- Standard Ebooks serves an HTML "your download has started" interstitial instead of the file unless the download URL carries `?source=download`. Sanity-check downloaded EPUBs by their `PK\x03\x04` magic bytes.
- Gutenberg's stable per-format URLs are `https://www.gutenberg.org/ebooks/<id>.epub3.images` and `<id>.txt.utf-8` (both redirect to the cache; follow redirects).
