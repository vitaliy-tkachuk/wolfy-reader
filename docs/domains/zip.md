# ZIP domain

## Overview

From-scratch ZIP container reading in `src/zip`: locate the end-of-central-directory (EOCD) record, walk the central directory, verify local file headers, and hand back exact entry bytes. Built from the PKWARE APPNOTE structure definitions only — no code from other zip implementations. Public surface: `openZip(source) → ZipArchive` (`entries`, `entry(name)`, `read(name)`), the `ZipSource` input union, and the typed errors, all exported from `src/zip/index.ts`.

## Key decisions

- **Inflate is `DecompressionStream('deflate-raw')`** — the platform primitive, never a hand-rolled RFC 1951 decoder. This sets the browser baseline (see `docs/architecture.md`) and keeps the reader dependency-free. Node ≥18 ships the same global, so the suite runs headless.
- **Everything flows through one range-read shape.** `ArrayBuffer | Uint8Array | Blob | { read(offset, length), size }` all normalize to an internal `ByteSource` (`src/zip/source.ts`); no code path ever assumes the whole file is in memory. The range-reader form requires `size` because EOCD discovery starts from the file tail — a length-less stream cannot be seeked to its end.
- **The central directory is authoritative for sizes and offsets.** Local headers are verified (signature, own name/extra lengths) but their size/CRC fields are never trusted — data-descriptor entries (general-purpose flag bit 3) legitimately zero them.
- **Local error taxonomy, defined here:** `ZipError` (base) with `ZipFormatError` (malformed/missing structures, truncation, corrupt deflate), `ZipEncryptedEntryError`, `ZipUnsupportedMethodError`, `ZipEntryNotFoundError` (`src/zip/errors.ts`). These are domain-local on purpose; bridging into the core taxonomy is a separate seam.
- **Encrypted entries list but never read.** Flag bit 0 marks the entry `encrypted: true` in the listing; `read()` rejects with `ZipEncryptedEntryError` before any byte of payload is fetched. No decryption ever (DRM-free is a permanent project rule).
- **Fixtures are generated by multiple tools** (`scripts/make-zip-fixtures.mjs`: bsdtar, PowerShell `Compress-Archive`, plus a byte-level Node writer) because different writers emit genuinely different header shapes — that variance is the main real-world risk for EPUBs.

## Implementation notes

- **EOCD scan** (`src/zip/eocd.ts`): read the last `min(size, 1024)` bytes, scan backward for `PK\x05\x06`, accept a candidate only if its comment length reaches exactly to end-of-file; escalate once to the spec maximum tail (`22 + 65535`) if not found. Opening an archive therefore costs two range reads (tail probe + central directory) in the common case.
- **zip64**: after the EOCD is found, look for the zip64 locator (`PK\x06\x07`) in the 20 bytes before it (read from the tail buffer when possible); if present, entry count / CD size / CD offset come from the zip64 EOCD record (`PK\x06\x06`) instead. In central records, fields masked with `0xffffffff` are replaced from the `0x0001` extended-information extra, whose payload holds values *only* for the masked fields, in fixed order (uncompressed, compressed, offset). Masked EOCD fields without a locator are a `ZipFormatError`.
- **Entry read**: reject encrypted → read the 30-byte local header at the central directory's offset → verify `PK\x03\x04` → compute the data offset from the *local* header's name/extra lengths → read exactly `compressedSize` bytes → method 0 passthrough or method 8 inflate → verify the decompressed length matches the central directory. Any other method is `ZipUnsupportedMethodError`.
- 64-bit values go through a `Number.MAX_SAFE_INTEGER` guard (`toSafeNumber`); multi-disk fields are rejected as unsupported.
- Every range read is bounds-checked and length-checked (`readExact`); a short read from a host range reader surfaces as `ZipFormatError`, not silent corruption.
- Tests (`test/zip.test.ts`) assert exact byte-for-byte round-trips against the committed source files in `test/fixtures/zip/content/`, and a recording range-reader over `node-range.zip` + its layout manifest asserts opening touches only tail + central directory and an entry read stays inside that entry's local-header+data span.

## Gotchas

- **PowerShell 5.1 `Compress-Archive -CompressionLevel NoCompression` does NOT produce method 0** — it emits method 8 whose deflate stream is all stored blocks. A genuine stored fixture needs bsdtar (`zip:compression=store`) or the byte-level writer.
- **bsdtar (libarchive, Windows' built-in `tar.exe`) always writes data descriptors** (flag bit 3, zeroed local sizes/CRC), even to a seekable file — and its zip64 mode writes the zip64 EOCD record + locator while leaving the classic EOCD fields *unmasked*. Both shapes are covered by committed fixtures; never assume "zip64 present ⇒ classic fields are `0xffffffff`".
- The local header's name/extra lengths can differ from the central directory's copy (bsdtar pads local extras) — always compute the data offset from the local header itself.
- Entry names without the UTF-8 flag (bit 11) are cp437 by spec; `TextDecoder` has no cp437, so names decode as non-fatal UTF-8. Identical for the ASCII names real ebooks use; exotic cp437 punctuation would garble.
- The EOCD tail probe legitimately overlaps trailing entry data in small archives (the last 1024 bytes usually include the last entries). Range-touch assertions must scope "don't touch other entries" to entry reads, not the open probe.
- `BufferSource` excludes `SharedArrayBuffer`-backed views, so bytes are re-backed via `slice()` before entering `DecompressionStream` — a host range reader may return SAB-backed views.
- `Buffer` and `Uint8Array` fail `assert.deepEqual` prototype checks against each other; tests re-wrap `readFile` results as plain `Uint8Array`.
- Fixture stability across clones relies on the repo-wide `eol=lf` normalization: the committed `content/*.txt` are LF-only, and `.zip`/`.bin` fixtures contain NUL bytes so git auto-detects them as binary. Keep fixture text LF-only.
