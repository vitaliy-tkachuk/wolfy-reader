# Architecture

> This file holds global architecture **and** cross-cutting decisions (stack, database, auth, deployment, API style, etc.) woven into the section each affects — date significant ones inline. Domain-local decisions live in `docs/domains/<domain>.md` instead. There is no separate decisions folder.

## Purpose

Read ebooks in the browser — with pages that turn, text you can search, and typography you can change without losing your place.

wolfy-reader renders ebooks in the browser — EPUB, FB2 and plain text — with paginated and scrolled reading, chapter and TOC navigation, in-book search, and live appearance controls for font, theme and margins. It is built from scratch on platform primitives, carries zero runtime dependencies, and treats its API as a promise rather than a moving target: the `Book` model and the `Position` format are covered by semver. Reading position survives font-size and layout changes, and untrusted book content renders inside a hardened sandboxed iframe. It targets developers who want a reader that is small, pleasant to use, and safe with untrusted files — not a spec-conformance or DRM reading system.

## Current stack

- Language: TypeScript — ESM only (`"type": "module"`), no CJS build
- Build system: TypeScript compiler (`tsc`) emitting plain ESM to `dist`, no bundler; `node:test` for tests, Playwright for browser tests, esbuild for the packaging and size-budget assertions (all dev-only)
- Package registry: npm — `wolfy-reader` (unscoped; availability confirmed)
- CI / release: GitHub Actions — checks on every push and pull request; releases are Conventional-Commit-driven via release-please, published by OIDC trusted publishing with provenance and no stored token (2026-09-16)
- Target platforms / runtimes: Browsers with `DecompressionStream` — Chrome 80+, Safari 16.4+, Firefox 113+
- CI: GitHub Actions (2026-09-16) — typecheck, the guards, the headless `node:test` suite, the build, the size budget and the pack-fidelity check on every push to `main` and every pull request; the Playwright tier on pull requests only. Node is pinned by `.nvmrc` so local and CI cannot drift. **There is no lint job, because there is no linter**: formatting is hand-maintained by rule, so CI enforces the constraints a reviewer cannot see (dependency count, layer boundaries, bundle size, packaged shape) rather than the ones a reviewer can. See [`docs/domains/release.md`](domains/release.md).

## Main application areas

The source tree exists as scaffolding; decoders, paginator and view fill the directories milestone by milestone:

- `src/core` — the stable contract: `Book` model, `Position`, `TocItem`, typed errors, the `open()` entry point and format-registry seam
- `src/zip` — from-scratch ZIP container reader built on `DecompressionStream('deflate-raw')`
- `src/formats` — per-format decoders (`epub`, `fb2`, `text`), each producing a `Book`
- `src/layout` — the paginator: chunked, virtualized CSS multi-column
- `src/view` — the renderer and hardened sandboxed-iframe host: `ContentHost` turns a `Section` into live markup in an opaque-origin frame
- `src/react` — React 19 bindings over the reader facade (`useReader` hook + `Reader` component), written without JSX, published as `wolfy-reader/react` with React as an optional peer. See [`docs/domains/react.md`](domains/react.md)
- `test/fixtures` — small, license-clean book fixtures (committed), including the hostile EPUB and the machine-readable vector manifest the view's security tests iterate
- `test/browser` — the Playwright tier: the harness page plus the suites for anything a browser is load-bearing for (`npm run test:browser`)
- `test/corpus` — Project Gutenberg / Standard Ebooks corpus (gitignored, downloaded by `scripts/fetch-corpus.mjs`)
- `demo/index.html` — framework-free decoder proof and the primary development surface: opens a book through the public API and shows metadata, cover, TOC and reading order, and renders a chapter as live markup inside the sandboxed host, alongside a report of what the sanitizer removed and what the CSP blocked
- `docs` — architecture, domain docs, workflow

## Important boundaries

- **`src/core` is the stability promise** (2026-08-24). The `Book` model — optional metadata (`title`, `author`, `language`, `cover`), a `TocItem` tree, sections in reading order, a resource map, and optional presentation flags (`direction`, `fixedLayout`, and `scripted` per section) — and, once it lands, the `Position` format are the semver contract; everything else may churn. Names in `src/core` are frozen as if they can never be renamed, and carry no format's vocabulary. **Core is also headless by rule**: nothing reachable from `src/core/index.ts` may import `src/layout` or `src/view`, in either value or type position, so a Node consumer importing the core entry can never load a module that touches `document`/`window`. `npm run check:core` enforces it mechanically — see [`docs/domains/tooling.md`](domains/tooling.md).
- **The `exports` map is what enforces public-vs-internal at runtime, so it is written longhand** (2026-09-16). The package publishes exactly six subpaths — `.`, `/core`, `/epub`, `/fb2`, `/text`, `/react` (plus `./package.json`) — with no wildcards, because a wildcard would publish the whole tree and make every internal module something a consumer can depend on. **`/react` is the only subpath that imports a framework, and React is an optional peer** (2026-09-17): `peerDependenciesMeta.react.optional` is what stops npm auto-installing React into a consumer that only wanted a decoder, `check:guards` refuses a peer that is not optional, and `check:pack` asserts the tarball install brings in no peer. No other subpath may import `react`; the root's size budget would catch it. **`.` carries the reader facade together with the core surface**: `render` takes a `Book` and `open` is the only public way to make one, so splitting them would make the common case a three-import dance. Both resolve to the same emitted modules as `/core`, so there is one `open`, one `Position` model and one set of error constructors however a consumer reaches them — `instanceof BookError` holds across entries. **`/core` stays the headless entry**: the root reaches `src/layout` and `src/view`, and only `/core` carries the guarantee `npm run check:core` enforces, so headless consumers are pointed there. **Each format decoder is its own subpath rather than a barrel**, because their closures differ by an order of magnitude (`text` 3 modules, `fb2` 10, `epub` 20 — only `epub` pulls the ZIP reader) and a barrel costs exactly the consumers who do not bundle. None of this is observable from the source tree: the demo and the browser harness import `/src/...` by path, which `exports` does not govern, so **`npm run check:pack` — which packs, installs the tarball into a scratch consumer, then imports and typechecks every subpath — is the only thing that exercises the published shape**. See [`docs/domains/release.md`](domains/release.md).
- **The `Position` format is version-first and host-opaque** (2026-08-25). A reading position serializes to a single opaque string — a `wr1:` version prefix followed by a JSON payload whose first field is also a version discriminator — that a host persists verbatim and never parses. The redundant version signal is the mechanism that lets the format evolve without breaking already-stored positions, which is why it ships first rather than added "for later". A `progress` number (0..1) travels on the `Position` object alongside the string so host UI (scrollbars, "42%") never decodes it. The position is content-addressed: it is backed by a Hypothesis-style text anchor (exact quote + prefix/suffix context) and matches by content, with a grapheme offset used only to break ties between identical quotes — because text survives reflow and font changes while character positions do not. **A structural fault (a malformed or unknown-version string) throws `CorruptContainerError`; a live-content resolution miss is a value, never an error** — the same not-found-is-a-value split the model already draws with `Section.resolve()`, which returns `undefined` rather than throwing. Capture is headless by rule: it consumes caller-supplied plain text and a UTF-16 offset, never HTML or the DOM. See [`docs/domains/position.md`](domains/position.md).
- **The frozen surface grew deliberately for reference resolution: `Section.resolve?()` then `Section.resolveHref?()`** (2026-08-24 / 2026-08-26). Sections carry an optional `resolve(reference: string): Resource | undefined` — the format maps a reference *as it appears inside that section's own content* to the resource it names. It was added because rendering book content needs images, stylesheets and fonts, and nothing in the model could answer "what resource does `../images/foo.jpg` in this section refer to?" — the direct consequence of removing paths from the model. The two alternatives were both worse: a path-keyed resource map would put container paths back into a format-neutral model, and shipping the view with no resource loading would render books unstyled and imageless. It is optional and additive, so no existing consumer changed. Additive growth of `src/core` is allowed when the alternative is leaking a format's vocabulary into the model; renames and removals still are not. It grew the same way a second time with **`Section.resolveHref?(reference): SectionRef | undefined`** (2026-08-26) — `resolve`'s navigation twin: `resolve` yields a reference's *bytes*, `resolveHref` yields the *section* it targets (`{ sectionId, fragment? }`, still path-free). It was added because in-book links (a "next chapter" anchor, a rendered table-of-contents entry) point at another section, and the facade could otherwise only guess the section from the href by matching an opaque manifest id — so cross-file chapter links silently did nothing. Same optional/additive/soft-miss discipline; see [`docs/domains/core.md`](domains/core.md) and [`docs/domains/epub.md`](domains/epub.md).
- **The frozen surface grew a third time, for three facts a host cannot derive: `Section.linear?`, `BookMetadata.identifier?`, and `Uint8Array` input** (2026-09-17). Same discipline as `resolve`/`resolveHref` — optional, additive, soft defaults, no rename and no removal — and each member is named for the general ebook notion rather than the format that prompted it. **`Section.linear?: boolean`** is `false` only when the book places a section outside its primary reading flow (EPUB spells it `itemref[linear="no"]`: cover pages, footnote files, answer keys), omitted otherwise, so "linear" stays the default and no existing book changed shape. It exists because such a section must remain *addressable* — a TOC entry or an in-book link still targets it — while a host paginating straight through should be able to skip it, and nothing in the model could tell the two apart. Deciding for the host instead, by dropping those sections from `sections`, would have quietly redefined a reading order the model promises is complete. **`BookMetadata.identifier?: string`** is the identifier the book declares for itself (EPUB's `dc:identifier` chosen by `unique-identifier`, else the first non-empty one; FB2's `document-info/id`; plain text declares none and omits it). The library never persists, so a host that wants a reading position to survive a reload must key the opaque `Position` string it stores against *something*, and the model offered only a title — neither unique nor stable. A file name is the host's claim about the book; the identifier is the book's claim about itself. It is trimmed of surrounding whitespace, unlike the verbatim copy the EPUB font-obfuscation key derives from, because a storage key must be the same string on every open. **`Uint8Array` joins `BookInput`** because `fetch().bytes()`, `readFile` and the zip layer already speak it, and rejecting it taught callers only to append `.buffer` — which is wrong for any view that does not span its whole buffer. A `SharedArrayBuffer`-backed view is re-backed with `slice()` during normalization, mirroring the zip layer's inflate path: `BufferSource` excludes SAB, so the platform primitives downstream would refuse it. See [`docs/domains/core.md`](domains/core.md).
- **Untrusted book content renders behind three independent defences, and none of them may be dropped for convenience** (2026-08-24). The frame is `sandbox="allow-scripts"` with no `allow-same-origin`, so its origin is opaque; content is parsed, normalized and sanitized against an **allowlist** of elements and attributes before it is ever assembled; a per-render `<meta http-equiv="Content-Security-Policy">` sets `default-src 'none'` with a nonce for the host's own coordination script; every in-book resource is served as a `data:` URL; and host↔frame traffic is one typed, versioned, validated `postMessage` protocol. The layers are not redundant. `allow-scripts` is granted to the *document*, not to a party, so book script would run under the same grant as the coordination script and could impersonate it on the shared message channel — a sandbox cannot tell them apart, only sanitization can. Equally, sanitization alone cannot stop egress, which is the CSP's job. **Sanitization never consults `Section.scripted`**: that flag is an author declaration a hostile book simply omits. Mechanism and rationale live in [`docs/domains/view.md`](domains/view.md).
- **The model is format-neutral by rule** (2026-08-24): sections are id-addressed lazy byte payloads with a media type, not file paths; TOC entries target `sectionId` + optional `fragment`, never an href; the cover is data (`Resource`: media type + lazy bytes), never a container path. This is what lets single-XML-file FB2 and file-less TXT share one model with EPUB, and would let a record-based container such as MOBI do the same. See `docs/domains/core.md` for the per-shape rationale.
- **No format is baked into core.** `open(input, { formats })` takes an explicit format list; a format is a `BookFormat` (sniffer + decoder over a normalized `ByteSource`), and third-party formats register through exactly the same public seam as built-ins. Sniffers run in registration order; the first claim wins.
- **Bytes in, `Book` out.** Input is `ArrayBuffer | Uint8Array | Blob | File | RangeReader` (an object `{ size, read(offset, length) }` — size is required so tail-anchored containers like ZIP can locate their end structures), normalized once into `ByteSource`. The library never fetches and never persists; the optional `StorageAdapter` is host-implemented and only ever *called* by the library, via the decoder's `FormatContext`.
- **Failures are typed.** Every library error extends `BookError` (`UnrecognizedFormatError`, `CorruptContainerError`, `EncryptedContentError`); `open()` wraps any untyped decode failure in `CorruptContainerError` with `cause`, so hosts always catch by class.
- **The reader facade is a free function outside core, not a method on `Book`** (2026-08-25). The PLAN §4 sketch shows `book.render(element, options)`; that method cannot exist, because `Book` lives in `src/core` and core is headless by rule — nothing reachable from `src/core/index.ts` may import `src/view` or `src/layout` (`npm run check:core`), and `render` must drive both. The shape is therefore relocated to `render(book, element, options): Reader`, exported from `src/reader` (a view/layout-side subpath, not core), keeping the sketched object surface (`next/prev`, `nextSection/prevSection`, `goTo`, `back`, `position`, `mode`, `on`, `setMode`, `setAppearance`, `destroy`). The facade owns no format vocabulary, never fetches and never persists: a `Book` comes in, page geometry comes from the `Paginator`, positions are the headless `Position` model, and it never reaches past the paginator into frame geometry. Its public surface — including the event names, payload shapes, and firing order — is frozen under the 0.x contract; mechanism lives in [`docs/domains/view.md`](domains/view.md). The surface grew once more, additively, to carry live appearance: `setAppearance(appearance)` plus the `Appearance` type and the `theme`/`customProperties` reader options (2026-08-25). Additive growth of the frozen surface is allowed where it does not rename or remove; the appearance mechanism (the `--wr-*` contract, the cascade strategy, and why theme injection needs no CSP or protocol change) lives in [`docs/domains/appearance.md`](domains/appearance.md). It grew additively again with `search(query, options?)` (2026-08-25) — whole-book full-text search returning a lazy async iterator of jumpable `SearchHit`s (`{ text, context, position, sectionIndex }`), streaming as sections are scanned and never buffering the book whole. The matching engine is **headless** (`src/search`, importing only `src/core` + platform primitives — it passes `npm run check:core`'s spirit) and the scan does **not** cross the frame boundary, so search touches no wire message and `PROTOCOL_VERSION` is unchanged; mechanism lives in [`docs/domains/search.md`](domains/search.md). The `selection` event grew additively too (2026-09-17): its payload carries `rect`/`rects` — the selection's bounding box and visible line boxes, in CSS px relative to the reader element's padding box, clipped to the visible page — because the host cannot measure a selection that lives behind the opaque origin, and a highlight menu has to be anchored somewhere; the menu itself stays host code, like every other annotation UI (see [`docs/domains/view.md`](domains/view.md)). Its counterpart `selectionclear` (2026-09-17) is the same additive growth from the other side: it fires exactly once when a reported selection is gone — collapsed by a bare click behind the opaque origin, which no host can observe, or lost with a replaced frame document — with an empty payload, so a host can dismiss whatever it anchored on `selection` without the library knowing what that is; it is a new event rather than an empty `selection` because `selection`'s payload is a promise of non-empty text and a resolvable `Position`, and it took the protocol to v12 (`selectioncleared`). Two tap reports followed (2026-09-17): `decorationtap` — the decorations under a tap, most recent first, each with its visible geometry — because a highlight menu has to open on the highlight itself (the Kindle/Books gesture) and only the frame can hit-test overlays behind the opaque origin; and `tap` — the point of a plain tap, emitted **before** the tap-zone navigation it may trigger — so a host can dismiss its own UI before the page moves. A decoration tap never turns a page, exactly like a link or image tap; the menu stays host code. `decorationtap` is a new frame→host message (protocol v13); `tap` reuses the existing wire message. It grew additively once more with `decorate(id, position, { className })` / `undecorate(id)` (2026-08-25): **the library DRAWS decorations but never stores annotation data — storage is the host's, by design.** A decoration is a styled overlay painted over the range a content-anchored `Position` resolves to; the reader holds the decoration *intent* (id → position + class) in memory only, so it can re-anchor the overlay across a re-layout, and drops it on `undecorate`/`destroy` — it never serializes, persists, or fetches annotation state. This is the same "bytes in, `Book` out, never fetches, never persists" boundary applied to annotations: a host that wants durable highlights stores the `Position` strings itself and re-calls `decorate` on the next open, and all annotation UI (notes, colour pickers, comment threads) is host work outside the library. Decorations cross the sandbox as two host→frame wire messages, so they are a protocol growth of the frozen reader surface, not a new persistence surface. The host↔frame protocol reached **v4** over M2-3/M2-4 (adding `goToPage`, `offsetOfPage`, `offsetOfElementId`, `pageOfOffset`, `sectionText`, `relayout`, and link-click reporting on top of the M2-2 handshake); it is a single typed, versioned, validated channel, and both ends' validators are bumped together by hand.
- **Position preservation across appearance changes is an invariant, not a hope** (2026-08-25). `setAppearance` and `setMode` are position-preserving **by contract**: every reflowing knob (font size, family, line height, margin, columns) and the paginated↔scrolled mode switch captures a content anchor for the current page, re-lays out, resolves that anchor against the new layout, and seeks back to the page it now lands on — the mechanism is the `Position` content anchor (exact quote + context), never a page number, because reflow moves page numbers but not prose. **The tolerance is stated as the paragraph at the TOP of the page**, because the restore anchors on the page-*start* offset (`positionOfPage` → `offsetOfPage(page)`): the reading place you were at is held, though a paragraph lower on the old page may legitimately move to an adjacent page when the column count changes. A same-text resolution miss degrades soft to page 0, never an error. This is proven, not asserted: a parameterized Playwright suite (`test/browser/appearance.browser.mjs`) runs every knob × the mode switch × two corpus books × two starting positions, and a deliberate-regression case asserts the invariant assertion itself *throws* when the restore is skipped — so the suite guards the invariant instead of passing vacuously. If a case cannot pass, that is a layout/position bug to fix, never a tolerance to widen. Scrolled mode holds the same tolerance: entering it scrolls the anchor's glyph to the top of the viewport, and leaving it (or reflowing/resizing while in it) captures the glyph at the *live* scroll offset — including one the reader scrolled to by hand — so a paginated→scrolled→paginated round trip lands on the page it left. Mechanism and the stated tolerance live in [`docs/domains/appearance.md`](domains/appearance.md), [`docs/domains/layout.md`](domains/layout.md) and [`docs/domains/position.md`](domains/position.md).
- **TTS is out of scope but enabled — sentence ranges + the highlight primitive, never speech** (2026-08-25). The reader surface grew additively once more with `sentences(): Promise<readonly SentenceRange[]>`, backed by a headless `segmentSentences(text, sectionId, options?)` in `src/core` (a `SentenceRange` is `{ text, position }`, the `Position` anchored over the *whole* sentence so `decorate` highlights all of it, not just its start). This is the M3-6 enabler: a host pairs each sentence's `Position` with `goTo` (jump) and `decorate` (highlight) to drive a speech engine sentence-by-sentence over the reading view — the library speaks nothing, fetches nothing, and stores nothing. `sentences()` reads the same frame-measured section text decorations resolve against, so a sentence both jumps and highlights cleanly; the segmentation itself is pure `Intl.Segmenter` in core, so it stays headless (`npm run check:core`). Additive growth of the frozen 0.x surface, no rename/remove. Mechanism lives in [`docs/domains/position.md`](domains/position.md) and [`docs/domains/view.md`](domains/view.md).

## Known constraints

- **MOBI/AZW3 are not supported, and not planned** (2026-09-17). The case for a from-scratch decoder was uniqueness — no stable, MIT, zero-dependency MOBI reader exists — but the population it would serve is small and shrinking: Amazon's current format (KFX) is closed, every Amazon-sold book is DRM-locked and therefore out of scope anyway, and the DRM-free remainder (Project Gutenberg, Calibre output) converts losslessly to EPUB. Weeks of work — PalmDB, PalmDOC and HUFF/CDIC decompression, MOBI 6 and KF8 — for a fifth selling point that none of the four load-bearing ones (zero deps, stable API, position stability, search) depend on. The format seam is public, so a third-party `BookFormat` can add it without a change here; if Kindle files show up as `UnrecognizedFormatError` in a real consumer, that is the signal to revisit, and a header probe of Gutenberg's Kindle editions showed PalmDOC compression throughout, so HUFF/CDIC would be skippable.
- **Fixed layout is detected, never rendered** (2026-08-24). `Book.fixedLayout` records that a book declares fixed-size pages so a host can refuse it or hand it elsewhere; rendering stays reflow-only, permanently. There is no partial fixed-layout path and none is planned.
- **Range-reader inputs must supply their total size.** Tail-anchored containers (ZIP's end-of-central-directory) cannot be located otherwise.
- **A chunk cannot be a block in a shared column flow** (2026-08-24). `content-visibility: auto` applies layout containment, and a layout-contained box cannot fragment across columns — it collapses to a single column and clips the rest. The paginator therefore gives each chunk its own multi-column context, which makes every chunk boundary a forced page break (measured cost: +8–16% pages). This constrains the sandboxed-iframe host and the page↔position mapping built on it. Measurements and the go decision live in [`docs/domains/layout.md`](domains/layout.md).
